# 投递、回执与故障恢复的人工验收

本页供测试人员通过上层 API 验收后续实现。路径、动作名和 JSON 取自候选接口，执行时替换为受测版本公布的契约，示例中的 ID 替换为上一步返回的值。下文给出预期结果，实测状态和计数由执行者填写。[资源管理与投递](../spec/reference/contracts.md#资源管理和事件投递) · [候选 REST 目录](../design-review.md#rest)

## 准备与观测

| 谁来做 | 准备什么 |
| --- | --- |
| 测试人员 | 使用案例专属的值班 Agent A、归档 Session S 和普通调用者。准备另一个禁止该调用者投递的目标 X，以及可以核实 X 收件情况的独立授权观察者。交办约定写清需要最终报告、保存结果或确认送达。每次测试记录 Event、Delivery、Run、ToolCall 以及外部作业的实际 ID。 |
| 部署与故障夹具 | 在隔离实例上提供可控时钟、可重复的模型响应、可按不同恢复能力配置的 CI、计数审计插件和可模拟确认丢失的通知接收方。CI 分别记录提交请求次数和实际创建的作业数，通知端分别记录收到的请求次数和有效通知数。准备在指定步骤暂停、重启或替换 worker，并能核实故障确实命中该步骤。 |
| 结果核对 | 人员从 API 查业务结果，部署人员提供订阅、外部计数及故障点记录。若接口未暴露某项观测，附上获授权的审计记录并注明观测来源。缺少故障或下游证据时，该分支记为待验证。 |

**通用请求。** 先用 `POST /api/events` 上报可唯一识别的测试输入，记下返回的事件标识。以下两次调用演示同一事实的归档与交办，各自使用独立的投递幂等键。后续案例可复用第二种写法交办。

```http
POST /api/events/{event_id}/deliveries
Idempotency-Key: R01-archive
Content-Type: application/json

{"target":{"session_id":"S"},"action":"attach"}
```

```http
POST /api/events/{event_id}/deliveries
Idempotency-Key: R01-work
Content-Type: application/json

{"target":{"agent_id":"A"},"action":"start_run"}
```

通过 `GET /api/events/{event_id}/deliveries`、`GET /api/event-deliveries/{delivery_id}` 分别查目标、入箱和处理结果。交办被处理后，从结果取实际 `run_id`，再查 `GET /api/runs/{run_id}` 及该 Run 的 `tool-calls`、`model-calls`。后续提到“一次分析”时，按该等待对应的逻辑推理决定计数，并与模型夹具收到的分析请求核对。[投递示例和候选查询](../goal-shaping/archive/loom-agent/2026-11-23-initial/overview.md#event-delivery)

## R01　同一事实直接归档和交办

按通用请求发送两项投递，再以各自原键原文分别重发。查询原 Event、两项 Delivery 及目标收件。应有一份来源事实、两笔独立收件。S 留下原 Event 引用，归档新增 Run 为 0，A 的交办形成 1 个 Run。再由普通调用者对 X 单独发起投递，查看可见的拒绝或处理失败，由授权观察者核实 X 新收件为 0。前两项仍各有原记录。[事实、入箱与交办](../spec/architecture/runtime.md#从收到消息到发起推理)

## R02　定时安排的生效时刻与重复触发

用 `POST /api/dispatches` 创建一份定时安排，设工作日 09:00、时区 `Asia/Shanghai`、目标 A、动作 `start_run`、内容“汇总夜间失败报告”。记录安排 ID 和生效修订。让夹具时钟从周一 08:59 跨到 09:00，并重放同一次到期通知。人员查询安排的 `evaluations` 和 `deliveries`。到点前新增交办为 0。本次到期能查到触发标识和规则版本，重复通知后有效投递和 Run 各 1。通过安排 API 暂停，越过下一次到点，目标新增收件为 0。恢复后观察下一次新到期，能与周一那次分别追查。[定时安排示例](../design-review.md#一份投递安排) · [安排的执行与恢复](../goal-shaping/archive/loom-agent/2026-11-23-initial/overview.md#message-ingress)

## R03　来源条件、脚本错误与投递权限

1. 建立只监听测试 CI 来源的安排。规则遇到成功报告返回空列表，遇到失败报告同时向 S 归档、向 A 交办。调用 `POST /api/dispatches/{id}/previews` 输入失败样例，预览两项目标后查实际投递，新增收件为 0。
2. 从获准来源先后上报成功和失败报告，重送同一来源的同一失败事件。查 `GET /api/dispatches/{id}/evaluations`、`GET /api/dispatches/{id}/deliveries`。成功报告有一次跳过记录。失败报告能按同一来源事件及规则修订查回两笔有效投递，目标各收一份，排查 Run 只有 1 个。
3. 用新触发分别执行能抛错的正式规则、请求越权目标 X 的规则，并另从一个未被选中的来源发同样的报告。抛错有独立的求值失败原因，新增收件为 0。越权可从校验或履行结果看到拒绝，由授权观察者确认 X 未收件。其他来源不触发这份安排。历史失败报告仍关联当时采用的规则修订。[投递规则与作用域](../goal-shaping/archive/loom-agent/2026-11-23-initial/overview.md#dispatch-rule)

## R04　CI 已创建作业，首个受理回执丢失

每行从新的普通 Run 开始，交办“提交测试并分析最终报告”。夹具让 CI 确实创建作业 T42，丢弃携带作业号的首个受理回执，在宿主还查不到 T42 时更换 worker。人员记下原 Run 和 ToolCall，接手后持续查询二者。表中 K 为原派发前保存并发送的稳定键。

| CI 夹具能力与动作 | 从 API 及 CI 账本核对 |
| --- | --- |
| 支持按 K 查询，在首次查询时返回 T42 | 新 worker 用原 K 查回 T42，关联到原 ToolCall。提交请求 1 次、实际作业 1 个。 |
| 仅保证有效期内，同键同参重提返回原作业号。让第二次请求正常响应 | 两次提交的键、参数、目标一致，实际作业 1 个。原 ToolCall 取回 T42。 |
| 无按键查询及有效幂等保证，随后补发可关联的迟到受理回执 | 补发前显示受理结果待核实，CI 提交请求始终 1 次。补发后 T42 归入原调用，原 Run 继续等报告。 |

三行都在受理后、最终报告到达前查询一次，应能看到等待。夹具再送达同一份含错误码 `E421` 的失败报告两次。每个 Run 各只登记一次后续分析，可查到 T42 的失败依据，CI 侧实际作业仍各 1 个。[CI 首回执专项验收](../spec/goals/v1.md#ci-lost-receipt-acceptance) · [工具恢复能力](../spec/reference/contracts.md#外部工具的恢复能力)

## R05　报告先于等待登记或与状态查询同时到达

用 Code Mode 同时发起查配置和等待最终测试报告两个子调用。夹具先返回配置，分别用两个新 Run 制造两种时序。第一组在等待记录即将登记时先送达最终报告，随后恢复登记。第二组先登记等待并更换 worker，让权威状态查询和最终回执同时带回同一报告。人员查原 Run 的父子 ToolCall 和分析用的实际输入。预期两组都能在原调用下查到正确的配置和报告，外层完成一次、后续分析各一次、CI 各建一个作业。两组之间分别记录 ID，避免把不同 Run 的报告归到同一等待。[并行调用与长等待](../spec/architecture/runtime.md#并行长等待和恢复)

## R06　事实已提交、首次分发前停机

让原 Run 等待报告，同时启用一个有权读取该报告的审计订阅。CI 发出报告，夹具在业务状态、Event 与发件箱记录提交后停机。本地模式在消费者首次读取该记录前停机，Redis 模式在首次 `XADD` 前停止发布进程。用原 HOME 恢复服务后，人员从原入口查报告 ID、原 Run 和审计的只读计数，并对照 CI 账本。预期恢复分发沿用原 `event_id`，业务报告事实 1 条，等待后的有效推进 1 次，审计记录 1 条，新增 CI 作业 0 个。夹具附故障位置证据。[事件分发约定](../spec/architecture/runtime.md#event-distribution) · [中断验收](../spec/goals/v1.md#event-distribution-acceptance)

## R07　消费成功后丢失确认，两组独立追赶

以新的报告重复 R06 的准备。让运行时订阅提交等待满足及后续动作，在确认消费前停机。让审计组处理，再启动继任者恢复运行时组。本地夹具让原发件箱记录重新送达。Redis 夹具在 `XACK` 前停机，再以相同 `event_id`、不同 Stream 条目 ID 重送。人员按原 ID 查报告、Run 的下一步和审计记录。预期业务报告仍为 1 条，审计记录和 Run 的有效推进各 1 次，夹具的分析模型只收到该步 1 次请求。两个组分别前进，插件观察产生的额外业务收件为 0。[重复送达与独立消费](../spec/goals/v1.md#event-distribution-acceptance)

切换后端时，在同一个 HOME 上用本地总线发一条事件，切到 Redis，核对原事件已补发到 Stream，再发第二条事件。切回本地后新增一个审计订阅，发送第三条事件。既有订阅应保留前两条的处理结果，新订阅能读到三条事件。第三条只在本地分发。[可执行用例](../../tests/acceptance_bus.py)

## R08　执行池竞争及 1、2、4 个 worker 对照

1. 默认启 1 个 worker。人员从同一 API 地址交办 A、B 两项独立工作。暂扣 A 的 CI 报告，让 B 的工作就绪。查到 A 仍等待、B 已执行，再释放报告，A 沿原 ID 接续。
2. 用同一程序分开运行入口与执行角色，启动至少 2 个共享状态的 worker，客户端保持原地址。让两个独立 Run 同时就绪。夹具另让两名 worker 竞争同一 Run 的同一版本，并重送唤醒事件。用执行时刻核对独立工作可以重叠，按竞争步骤的决定 ID 核对该步只提交一次，关联的模型或工具没有多执行一份。
3. 固定交办内容、并发请求数、测量时段及外部模型和 CI 时延，分别测 1、2、4 个 worker。用成功提交的独立就绪 Run 步骤数除以测量秒数，同一步重送只计一次。逐条配对“宿主接纳使等待满足的回执”和“对应下一步开始执行”两个时刻，报告配对时差的 p95。填写实测值和样本量，按三组结果比较。[执行池约定](../spec/architecture/runtime.md#worker-pool) · [并发与负载验收](../spec/goals/v1.md#worker-pool-acceptance)

## R09　补充、取消与迟到回执

分两次交办，每次等 CI 首先返回作业号。用 `POST /api/events` 上报控制消息，通过 `POST /api/events/{id}/deliveries` 投给**原 Run 所属 Session**，带原 `run_id`。第一组使用候选动作 `add_input` 补充“只分析本次失败，不重跑”。等补充已生效再释放报告，最终答复应带本次失败依据，CI 只建原作业。第二组先从错误的 Session 或无权身份请求取消，核实原等待仍有效。再由获准身份以 `request_cancel` 取消，确认已生效后发出两份重复迟到报告。查询原调用仍能追查报告。生效后新派发的模型和工具均为 0，原 Run 保持取消，不生成新的业务 Run。[补充与取消契约](../spec/reference/contracts.md#资源管理和事件投递) · [普通交办验收](../spec/goals/v1.md#单次交办能持续到履约)

## R10　待审批工具在重启后批准或拒绝

让测试工具提交必须人工批准的外部动作。人员查到待审批的原 Run、ToolCall 和拟执行参数，夹具确认远端执行次数为 0，再重启 worker。审批人通过现有事件入口提交针对原调用的决定，由宿主核对身份、作用域、参数和有效等待，具体事件载荷以实现公布的契约为准。

| 用新的待审批调用分别操作 | API 结果和外部计数 |
| --- | --- |
| 有权审批人重复批准同一项 | 两次决定关联原 ToolCall，实际派发一次、外部执行一次，回执归原调用。 |
| 有权审批人拒绝 | 拒绝作为该调用的终态错误交回直接调用方，结果可查，外部执行 0 次。 |
| 先以无权身份批准，再在取消生效后由有权审批人补发旧批准 | 前次不能满足待审批条件，后次可查决定已失效，外部执行 0 次。 |

拟执行参数若已变化，原批准也不能用于派发修改后的参数。[收件、等待与审批](../goal-shaping/archive/loom-agent/2026-11-23-initial/overview.md#event-consumer)

## R11　上层收到答复后确认丢失

先交办一次“检查通过就保存，只在失败时通知”，由夹具返回通过。查到成功结果，接收方收到的通知数为 0。再交办“失败时向本次指定目标确认送达”，把同一失败报告另投给仅作归档的 S。夹具让通知端收到答复，在交付器保存确认前中断。分别用新 Run 验证下表，恢复后查原 Run、相同答复、目标及交付标识。恢复交付产生的新模型调用、CI 作业和向 S 的通知均为 0。

| 通知渠道能力 | 核对送达结果 |
| --- | --- |
| 可按交付标识核实 | 交付器用原标识查回确认，接收方的有效通知 1 条，原 Run 达到确认条件后完成。 |
| 无法查询，但接收方可幂等去重 | 重发沿用原标识、目标和内容，接收请求可多次，有效通知仍为 1 条。 |
| 无法查询也无幂等保证 | 交付状态“送达待核实”可查。即使夹具知道对方收到，宿主也没有满足确认条件的依据。 |

[答复持久化与重试](../spec/architecture/runtime.md#并行长等待和恢复) · [外发确认和结果未知](../goal-shaping/archive/loom-agent/2026-11-23-initial/overview.md#event-consumer)

## R12　插件订阅、可见范围与总线替换契约

启用一个通过 `plugin:subscribe` 声明来源和类型的审计实例，令其可查询的测试记录按事件和订阅标识计数。由有权上报两个来源的人员分别提交订阅范围内的事件和同类型、来源越界的事件，再由夹具重送第一条总线通知。读取审计记录，获准事件产生 1 条有效记录，越界事件 0 条，插件观察新增 EventDelivery 与 Run 均为 0。停用该实例后再上报新事件，核实不再进入该订阅。宿主的其他独立订阅照各自权限及进度工作。[插件订阅契约](../spec/reference/contracts.md#插件工具与上下文)

先按默认本地模式运行，再显式选择 Redis Streams，以相同的插件声明、过滤条件和回调，用新事件分别重复 R06、R07。核对原事件身份、独立订阅进度、未确认条目恢复和业务提交后确认。另用同一 HOME 切换后端，令同一逻辑组重新见到已处理的事件，再提交新事件。检查旧事件仍只有一条有效业务记录，新事件能被该组处理一次。后端专有命令只由夹具处理。[消息总线适配器契约](../spec/architecture/runtime.md#event-distribution)

## R13　替换上下文构建插件，观察实际模型输入

部署人员准备两个可独立绑定的上下文构建实现。两者都保留原交办和必要材料，第二个实现额外选入一条已获准的测试资料 `CI-CTX-42`。保留同一推理触发策略、模型提供方和只观察模型完成事件的审计订阅。测试人员先后在两种生效配置下从同一 API 发起相同的新交办，以固定模型正常回答一次。查询两次 Run 的逻辑推理决定、ModelCall 及实际出站输入，再按调用 ID 对照模型夹具和审计记录。两次都只向选定提供方发出一次模型请求，测试标记只出现在第二份输入中。每次各有一条审计记录、一份对上层的答复。[推理与输入组装](../spec/architecture/runtime.md#从收到消息到发起推理) · [插件契约](../spec/reference/contracts.md#插件工具与上下文)
