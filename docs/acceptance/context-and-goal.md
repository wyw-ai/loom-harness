# 上下文、Goal 与模型交付验收

这里的用例面向调用 Loom 的聊天应用、API 客户端和获得授权的 Agent。每例可在独立 Session 重做。通过条件以实际交付、投递、模型输入和外部工具执行记录为准。本文列出待执行的验收步骤。对应的首版要求见[目标与验收](../spec/goals/v1.md#显式启用-goal-的交办)。

## 入口与取证

| 操作 | 验收时如何执行 |
| --- | --- |
| 建立会话、发送与查询 | 下文用 `S`、`R` 等代指实际返回的 ID。建会话可用 `POST /api/sessions`。每次“交办”先 `POST /api/events` 上报输入，再 `POST /api/events/{event_id}/deliveries` 投给指定 Session 并表达新交办。查询投递的消费结果取 `run_id`。补充或取消沿同一路径提交，指定所属 Session 和原 Run。 |
| 检查结果 | 查 `GET /api/runs/{id}`、`GET /api/runs/{id}/model-calls`、`GET /api/model-calls/{id}`、`GET /api/runs/{id}/tool-calls`。查 Session 的 `context/items` 和相应 Event 的 `deliveries`。每次记录操作前后的 ID、触发原因、可披露的输入或版本化引用，以及交付内容。聊天页面可用实际客户端，也可用调用相同 API 的测试客户端。 |
| Agent 工具 | `write_note` 等按 [Note 契约](../spec/reference/contracts.md#notes)作为当前 Session 授权工具调用。真人可发送明确要求让 Agent 调用，从返回值和 ToolCall 核对结果。它们的函数名不代表同名 HTTP 路由。 |
| 测试夹具 | 准备可记录请求的模型提供方、可按原作业号回调并统计提交次数的 CI 和两个可接手同一状态与文件的 worker。可让模型按脚本返回阶段答复、暂停摘要、重送同一决定或推迟浏览器收包。夹具负责制造时序和观测出站内容，这些操作均不要求开放管理生产 Run 的公网接口。检查私有标记时只在受控提供方查看测试数据。 |

下文给出的 HTTP 路径和请求字段沿用[接口评审目录](../design-review.md#rest)。除已确定的资源约定外，候选路径、动作名、故障类别和尝试次数均以被验实例提供的等价入口为准。各例说明的触发、权限、归属和可观察结果适用于这些入口。

## 上下文与分支

### C01 同一报告，一处留档、一处排查

1. 创建资料 Session A，选定获准排查的值班 Agent B。上报一份带唯一报告号的 CI 失败 Event E。向 A 投递 E 并选择仅留档，再将同一 E 投给 B，要求给出失败原因。按 E 查询投递，分别读取消费结果及 A 的历史。
2. 用获授权的用户创建带唯一标记的定时安排，按实例提供的 Agent 管理工具查到同一安排，变更未来生效的目标。使安排到期。另配置一个来源驱动的 Lua 规则，只把失败报告的指定材料投给 B。依次上报成功、失败报告，按安排查询实际投递和收件内容。

**通过**　E 有两个可区分的投递 ID，各自指向同一个 E。A 可读到资料且增加的 Run 为零。B 的投递消费后可追到一项排查 Run。定时投递落在更新后的目标。条件规则只对失败样本产生投递，B 收到约定材料。跨入口读取的是相同安排和生效配置。[投递契约](../spec/reference/contracts.md#资源管理和事件投递)

### C02 工具说明与材料选取反映在实际模型输入

1. 管理员启用测试工具集，为绑定该工具集的 Agent 注册可识别的指令段 `review-guide-v1`。创建 S，留下三份带不同标记的材料 A、B、C。通过测试上下文插件配置这一轮只选 C、A，按该顺序排列，并把 A 中的标记换成可识别的新文本。提交交办，读取实际 ModelCall。
2. 刷新指令段为 `review-guide-v2`，确认生效，向同一 S 再交办一次。撤出该段、确认生效，再交办一次。回读第一次调用和原始材料 A。

**通过**　三次出站的系统指令分别含 v1、仅含 v2、两者都没有。首轮所选材料按 C、编辑后的 A 排列，B 的标记缺席。原 Event A 和首轮出站记录都可复核其各自版本。可先用上下文预览定位差异，最终以实际请求判定。[系统指令与输入契约](../spec/reference/contracts.md#插件工具与上下文)

### C03 超出窗口只压缩选中的历史

1. 启用官方压缩插件。在 S 中用已完成的小步骤逐步积累可区分的历史，再交办“分析已有报告，只读”。让 CI 工具启动 T42 并保持未决。在该 Run 中投递一项要求现在回应的补充，例如“先列出已知现象，仍不要重跑”。
2. 夹具选用能容纳必要材料、容不下完整历史的模型窗口。待确实触发压缩后，读取该次主推理的实际请求、压缩产物覆盖的来源，再按源 ID 打开一条被覆盖的原始 Event。

**通过**　实际请求可被模型接纳，能读到当前要求、“只读”的限制、未决调用的原标识、T42 及其状态。能把摘要追溯到被替换的历史，原始 Event 可读。辅助摘要回到本次输入构建，单独返回摘要引起的额外主推理数和 CI 再提交数均为零。[压缩流程](../goal-shaping/archive/loom-agent/2026-11-23-initial/design.md#context-compaction)

### C04 从中间切点开分支，晚到的报告归原调用

1. 在父 Session P 的已选历史中准备 E1、E2、E3。父 Run 发起 CI 并等待报告。用 `GET /api/sessions/{id}/context/items` 取得包含 E2 的切点，以 `POST /api/sessions/{id}/branches` 按该位置创建子 Session Q。读取 Q 的来源与历史，并让 Q 根据其可见材料回答。
2. 用原调用关联上报父作业的终态报告。读取 P 和 Q 的运行、投递与工具记录。若父历史已生成覆盖 E1 到 E3 的摘要，重复从 E2 分叉并检查子模型实际输入。

**通过**　Q 有独立 ID 和交办，来源指向 P 的实际切点。Q 可见 E1、E2，不能从其继承的条目或摘要读到 E3 的唯一标记。父调用、等待和答复均由 P 接手，Q 未因分叉重派作业或自动取得切点之后的报告。[分支契约](../goal-shaping/archive/loom-agent/2026-11-23-initial/design.md#session-branch)

## 长任务 Goal

### C05 第 14 个模块之后主动续跑

1. 发起交办时显式选择 Goal，目标为迁完 20 个模块，完成条件为 20 个模块全部迁完且全量测试通过。夹具记录模块清单，使模型在完成 14 个、没有在途工具时给出阶段总结。读取原 Run、Session 收件和聊天历史，记下这次续跑的决定标识。
2. 让所选历史经压缩。夹具重送同一续跑决定，并对同一逻辑调用制造一次可安全重试的模型请求。比较每次实际输入和逻辑调用 ID。最后让模型读到 20 项完成清单和通过报告，显式标记完成。

**通过**　第 14 项的总结记为进度。主动续跑发生在原 Run，只有一个对应的持久推理决定和逻辑 ModelCall。每次尝试的实际输入都有有效目标及完成条件，且在所选历史之后恰有一条 `role=user`、来源为 `goal` 的说明。此决定新增的收件、EventDelivery 和聊天用户发言均为零。后续轮次按各自原因构建输入，旧说明不累积。满足条件并标记完成后，原 Run 按约定交付一次。[Goal 输入与留档](../spec/architecture/runtime.md#goal-续跑时模型收到什么)

### C06 等结果、取消及耗尽约定预算

1. 建立三个独立的 Goal Run。第一个只缺 T42 报告，停在工具受理后，暂不送报告。让 worker 处理完当前所有就绪工作。第二个也处于等待，通过真实事件入口向所属 Session 投递指向该 Run 的取消。确认取消生效后才送达它的报告。
2. 第三个设定实例支持并可核对的有限 Goal 预算，用阶段答复持续返回“尚未完成”。将其推进至已配置的上限，再重送上一个内部决定。分别读取三者的调用计数、状态及原因。

**通过**　第一个 Run 在报告到达前保持等待，调度空转产生的主推理为零。第二个显示取消，晚到报告能关联原调用，取消后新动作数为零。第三个显示因约定预算耗尽停止自动推进，未标记目标完成。重送未绕过预算。验收记录注明实际使用的预算种类及上限。[Goal 停止与等待条件](../spec/goals/v1.md#显式启用-goal-的交办)

### C07 压缩后的失败回执只唤起一次分析

1. 在迁移 Goal 中让 CI 实际受理 T42，把“已受理但报告未到”的历史纳入一次压缩。先查 ToolCall 和对端提交计数，再由 CI 来源带同一作业号、原调用关联，连续投递同一份失败报告两次。
2. 查该 Run 的决定与模型调用。打开用于分析本次失败的实际输入。若报告以引用提供，按该轮权限回读并和 CI 原件核对。

**通过**　原 Run 只增加一个由“工具回执满足等待”触发的失败分析决定。输入同时具备迁移目标、通过条件、原报告或可回读引用。该轮主动续跑说明为零。两份回执均可核对其归属，外部 CI 的提交次数始终是 1。[Goal 与上下文压缩](../spec/architecture/runtime.md#活跃-goal-与上下文压缩)

### C08 压缩中改口、取消或遇到不可恢复错误

1. 准备三个独立的 T42 失败分析 Run。夹具将三个模型窗口设为需要压缩，在摘要返回前暂停。对第一个通过真实投递补充“只分析，别重跑”。对第二个通过真实投递请求取消。读取受理结果，确认补充或取消已生效。随后释放含旧重跑建议的摘要，并重复送一次。
2. 对第三个使压缩以不可恢复错误结束，且受控模型窗口放不下原文。读三项 Run 的后续调用、出站输入、CI 计数和停止原因。

**通过**　第一个实际执行分析的输入含最新限制，旧建议导致的重跑为零。第二个仍可查到原失败回执，取消后增加的主推理和工具执行均为零。第三个能查到不能构建有效输入的原因，处理这个错误后自动重试停止。原文可以容纳时允许回退，不用这一分支冒充不可恢复失败。[采用摘要前的复核](../spec/architecture/runtime.md#活跃-goal-与上下文压缩)

## 输入框推荐

### C09 采纳、编辑、发送各产生什么记录

1. 启用推荐插件，让 Agent 交付“修改已提交到本地，尚未推送”。读取真实回复 ID 和版本，以空输入框调用 `POST /api/sessions/{id}/suggestions`，传 `after_reply_id`、`expected_version`。受控模型返回“推到远端”。
2. 在客户端采纳，改为“先看差异”。分展示、采纳、编辑三处检查收件与原 Run。最后点击发送，沿正常 Event 和投递入口查询用户实际发送的内容。

**通过**　推荐响应带本次取材版本。发送前消息历史和投递计数不变。点击发送后新增一条用户投递，内容恰为“先看差异”。生成、采纳和编辑推荐导致的推送次数均为零。[推荐接口](../spec/reference/contracts.md#输入框推荐)

### C10 服务端与客户端各自丢弃过期推荐

1. 在独立样本 A 中，基于回复 r42、版本 v18 请求推荐，夹具先扣住采样响应。客户端发送“先别推”，确认 Session 已受理，再让提供方返回旧建议。记录服务端回给客户端的内容。
2. 在样本 B 中，先让服务端生成有效的 v18 响应，在传给客户端前由夹具延迟响应。用户点击发送“先别推”、输入框按正常流程清空，再放行旧响应。在新样本上分别改为切换 Session、关闭推荐、已输入草稿三个条件，观察回包后的输入框。

**通过**　A 的服务端不交付旧候选文本。B 的客户端不因输入框重新为空而展示旧建议，切换会话、关闭推荐、已有草稿时也不展示或覆盖。两次发送试验中各新增一次真实投递，仅含“先别推”。由推荐引起的业务 Run、ToolCall 和远端推送数均为零。[推荐的时序约定](../spec/reference/contracts.md#输入框推荐)

### C11 推荐按调用者取材，采样没有执行权

1. 在同一 Session 放入用户 U 可见的已交付回复，以及仅 Agent 可见、带唯一标记的报告。让既有摘要包含该标记。以 U 的权限对相应回复请求推荐。受控提供方记录实际输入，并返回一个请求推送的工具调用。
2. 用获准读该报告的测试用户 V 请求相同版本，让夹具为 V 返回带其私有标记的文本，再以 U 重复请求。另起一次请求，让采样在途时撤销 U 的读取权限，然后放行。用有权限的独立样本分别模拟推荐额度耗尽和超时。

**通过**　U 的出站请求中既无私有标记也无泄露材料的受限引用。宽权限采样的候选不会提供给 U。撤权后不交付旧候选。模型请求工具时返回空建议，无原生、Code Mode 或 MCP 派发。超时或超额只影响该推荐。原答复仍可查，原 Run 和 Goal 状态无变化。[采样权限、限额与作用域](../spec/architecture/runtime.md#输入框推荐的只读采样)

## Note 与原始日志

### C12 写两份 Note，按描述分页检索

1. 在 S 中依次调用 `write_note("Release.[一]", "E421")`、`write_note("Release.[二]", "仅作备注")`，让创建时间可区分并保存两个引用。逐一 `read_note` 核对正文。
2. 用 `search_notes(limit=1)` 取首项，按返回的游标取下一页。在只含这两篇的测试 Session 再分别搜索 `Release.[`、`release.[`、`E421`。从无权读取 S 的另一 Session 尝试回读同一引用。

**通过**　两次写入得到可区分的引用。列表从新到旧，命中的元数据含引用、描述、创建时间、正文总行数。按字面搜索 `Release.[` 命中两篇，小写形式和仅在正文出现的 `E421` 都没有命中。全部列表和搜索结果均无正文。未授权者取不到原文。[Note 工具契约](../spec/reference/contracts.md#notes)

### C13 同一份 300 行日志从历史、Event 及另一 worker 回读

1. 在干净的 S 中发起作业“发布验收”。CI 返回超过自动外置阈值的 300 行已知日志，仅第 280 行含 `E421`。确认自动描述含“发布验收”、不含错误码。查 S 的 `context/items`，再查原工具结果 Event 的详情，对照 ToolCall、内容块、预览和 `note_ref`。重送同一回执。
2. 搜索 `E421` 和“发布验收”。由接手同一持久状态与文件的另一 worker 处理读取：给足预算，按原引用读全文、第 280 至 280 行、仅给结束行 2、仅给起始行 299。最后降低本轮输入预算使全文无法容纳，再请求全文并按同一引用缩小到一行。记录读取前后 Note 数和 CI 次数。

**通过**　两个历史入口及重送后仍引用同一原始内容块和 Note。搜索只有“发布验收”能命中这篇。全文逐行与 300 行原件一致。指定范围分别返回第 280 行、前两行和最后两行，文件头不占行号。超限返回明确原因、正文大小和总行数，缩小范围后能拿到完整行。读取过程新生成的 Note 为零，外部作业只运行一次。[日志回读验收](../spec/goals/v1.md#notes-acceptance)

## 模型选择、图片与结构化结果

### C14 首选不可用时，备选读取原截图并交付有效 JSON

1. 查询模型能力，给 Agent 配置首选 `chat-primary` 和支持图片、所需工具及输出格式的 `chat-backup`。先用普通请求确认实际选中首选。再上传一张只有图片像素中包含用例名 `checkout_retry`、错误码 `E421` 的截图。按“前置文字、图片、后置文字”上报输入并投递，交办时约定以下最终值 schema。

   ```json
   {"type":"object","properties":{"case":{"type":"string"},"error":{"type":"string"}},"required":["case","error"],"additionalProperties":false}
   ```

2. 为该 Run 设置测试顺序：首轮实际派发一次只读工具取得构建环境，中间工具按自身契约返回，例如数组 `["linux"]`。下一轮使首选模型发生被验实例允许切换的临时故障。记录备选提供方接到的原始请求，解码其中的图片或以提供方身份读取引用并核对像素。最后查询 Run 的结果和尝试记录。

**通过**　成功轮与故障轮均可核对实际模型。故障轮可区分首选失败与备选成功，仍属于同一 Run。备选收到可读原图，输入文字与图片的次序可核对。最终交付一次 `{"case":"checkout_retry","error":"E421"}`，可用交办方 schema 独立校验。已派发的环境查询只有原来的一次。工具返回的数组不参与最终答复的 schema 校验。[模型与交付契约](../spec/reference/contracts.md#模型与交付)

### C15 无兼容备选、附件不可读、最终格式持续错误

1. 分别创建三个 Run。A 使用同一图文输入，使首选不可用、备选只支持文本。B 使用有效的模型配置，但在实际读取前移除测试图片的可读权限。C 保持模型与图片可用，固定模型对 C14 的 schema 始终只给 `{"case":"checkout_retry"}`，包括实例允许的任何修正尝试。
2. 读取每个 Run 的调用、结果和失败原因。在受控的只支持文本的备选上检查收到的请求，在交付端检查成功答复。

**通过**　A 能查到没有满足要求的可用备选，未降为纯文本成功。B 可定位不可读图片，未凭文件名或空占位返回成功。C 在校验失败后给调用方明确结果，缺字段的值从未作为成功答复交付。不依赖特定重试次数或 HTTP 错误码。[模型、图片和结果验收](../spec/goals/v1.md#用户可指定模型图片输入和最终结果)

## 失败时可直接复核的反例

| 用例 | 任一观察即可判失败 |
| --- | --- |
| C01 | A 的留档投递启动推理，或仅修改一处安排却产生两个资源 ID。 |
| C02 | 预览已是 v2，出站仍含 v1。原 Event 被本轮输入编辑覆盖。 |
| C03 | 模型收到摘要后重新提交 T42，或无法定位曾被摘要覆盖的源材料。 |
| C04 | Q 的历史没有 E3，但其实际模型输入从父摘要读到了 E3 的标记。 |
| C05 | 用户没发新消息，聊天中却多出“继续”。或重试后输入含两条相同的续跑说明。 |
| C06 | 未到回执时模型不断自唤醒，或预算耗尽却显示 Goal 已完成。 |
| C07 | 相同失败报告触发两次分析，或回执唤醒轮被标为 Goal 主动续跑。 |
| C08 | 用户的限制已生效，迟到摘要仍使 CI 再次执行。 |
| C09 | 采纳即发出消息，或实际收到的是未经用户确认的原推荐。 |
| C10 | 清空输入框后延迟回包又显示旧建议。 |
| C11 | 只有 V 可见的标记出现在 U 的请求或响应里，或采样真的派发了推送工具。 |
| C12 | 搜索只出现于正文的错误码命中该 Note，或下一页仍返回第一篇。 |
| C13 | 第二个 worker 依赖第一个的本机路径，或超限读取不断生成新的 Note 引用。 |
| C14 | 最终 JSON 碰巧答对，但备选实际只收到图片占位文字，或工具在故障切换时被重复派发。 |
| C15 | 无法读取图片仍按成功交付，或缺少必填字段的输出通过宿主校验。 |
