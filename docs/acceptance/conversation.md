# 普通用户的一段会话

按[执行说明](README.md)创建本次测试范围。A01–A03、A07 核对现有首版职责。A04–A06 单列上轮评审提出、尚待定版的行为。文中 U 是普通用户，S 是 U 可访问的会话，R 是从投递消费结果取得的 Run。示例消息中的业务值可以替换为本次测试的唯一值。

## A01 从普通模板创建 Agent，问第一句话

**准备。** 测试部署已装配 `standard`、日常工具和一个可用模型。U 能创建自己的 Agent、开 Session 并交办。通过实例支持的方式显式选用该模型，记录生效的 Agent ID 和修订。模板省略模型另见 A04。

**操作。** U 查询可见模板，选 `standard` 的具体来源、版本，通过 Agent 创建入口创建 A，再创建 S。发消息“本次登记号是 QA-715。请只回复登记号。”先上报 Event，再向 S 投递新交办，指定 A 为响应者。查询 Delivery 直至取得 R，查 R 的最终答复。关闭客户端，重新以 U 登录，通过会话列表、S 的历史和 Run 列表查回该次答复。[HTTP 操作样本](conversation.http)

**通过。** 已收件、已关联 R、已完成可以分别识别。S 中这次新交办只产生一个 R，最终答复给出 `QA-715`。可核实实际模型。模型直接回答时，ToolCall 数为零。若真实模型自行使用工具，记录这次路径，再用可控提供方返回正常的无工具最终答复，单独核实直接交付。只读重连前后是同一条已交付答复、同一个 R，模型调用数没有增加。[普通交办验收](../spec/goals/v1.md#单次交办能持续到履约)

## A02 查一次真实报告，关掉客户端后追问“在哪一行”

**准备。** 给 A 绑定只读的 CI 报告工具。夹具预置 T42 的 300 行报告，正文第 280 行为 `E421`。开启大结果自动保存，U 有权回看本次报告。首问不提供错误码或行号。

**操作。** U 在 S 发新交办“查 T42 的失败报告，只告诉我错误码”。领到 R1 的最终答复后关闭客户端。重新连接 S 发新交办“刚才那个错误码在第几行？沿用刚才的报告”。保存第二次投递的 R2、其首个 ModelCall 的实际输入或授权引用，以及读到的对应原文。最后从原 Session 条目和原结果 Event 分别打开日志。

**通过。** R1 的 CI 工具实际执行一次，答复含 `E421`。R2 和 R1 属于同一个 S，ID 不同，R1 仍为已完成。R2 的输入能接上首问及答复或相应会话证据。沿原报告可定位第 280 行。两处回看指向同一 `note_ref`。CI 的查报告次数在追问前后保持一次。若仅碰巧答出 280、无可查的上下文或证据，不足以通过。[历史选材](../goal-shaping/archive/loom-agent/2026-11-23-initial/design.md#model-event-policies) · [Note 验收](../spec/goals/v1.md#notes-acceptance)

## A03 两个 Run 同时在等，只给其中一个改口

**准备。** 同一 S 内，U 分别交办“查 Windows 报告，失败时允许重跑”和“查 Linux 报告”。两次新投递各关联一个 Run（RW、RL）。受控 CI 暂缓两份报告。U 能查询二者。V 无权控制 S。

**操作。** U 将“只分析，先别重跑”作为补充投给 S 并显式关联 RW。等补充已受理，再让 Windows 失败报告到达。V 对 RL 请求取消，记录拒绝。随后由 U 取消 RL，待取消生效后让 Linux 报告迟到。查询两个 Run、原 ToolCall、模型输入和 CI 侧重跑次数。

**通过。** RW 的有效输入含新约束，仍能交付分析，重跑次数为零。V 的操作对 RL 没有影响。U 的取消只终止 RL 的新派发，迟到报告仍归原调用。S 中恰有本例的两个 Run，没有因补充、取消或回执出现第三项交办。重复查询不会唤醒任何 Run。[运行控制](../spec/reference/contracts.md#资源管理和事件投递) · [推进与交付](../spec/architecture/runtime.md#一轮推理结束后如何推进)

## A04 普通模板省略模型时的首轮体验（待定）

在全新的测试范围使用没有模型字段的官方 `standard` 样例。先给部署配置一个 U 获准使用的默认模型，按 A01 创建并发送“请回复 READY”。再用独立范围重复，第二组没有可用模型。保存创建响应、投递状态、实际模型或失败原因。

**建议判据。** 第一组能追到选中的模型并收到 READY。第二组能在创建或交办的明确步骤读到缺少可用模型的原因，上层可以结束等待。在模型解析规则落定前记录两组实测行为。[模板可选模型字段](../spec/reference/home.md#agent-templates) · [选模约定](../spec/architecture/runtime.md#模型与交付)

## A05 缺构建号时向用户澄清，回复只恢复原 Run（待定）

沿 A02 的准备另开 S，同时发起两项缺少构建号的排查。以 U 查询第一项的中间问题，记录问题关联及 Run。关闭客户端，重新打开这项问题后只回复“T42”，用同一操作标识重送一次，随后查看两个 Run 和实际 CI 请求。

**建议判据。** U 能识别第一项在等自己回答，重新登录后可定位同一问题。回复只恢复第一项一次并使其查到 T42。第二项继续等待，CI 只收到一次属于第一项的有效查询。最终报告到达前，第一项没有把反问当作最终交付。协议可用直接工具或等价的持久等待，由实际实现给出关联方式。[交互工具示例](../goal-shaping/archive/loom-agent/2026-11-23-initial/tools.md) · [等待与交付](../spec/architecture/runtime.md#一轮推理结束后如何推进)

## A06 关闭 Goal，普通模型持续重复调用（待定）

使用会重复请求同一只读工具的可控模型，配置本例主推理轮数上限为 3。关闭 Goal。U 在 S 发起一次交办。让首两轮工具实际返回结果，其中一次回执重投，并在两个就绪步骤之间切换 worker。读取最终状态、每个主推理决定及外部工具记录。

**建议判据。** 最多接纳 3 个主推理轮次，回执重送和换 worker 不消耗新轮次。额度耗尽生效后没有新派发，U 可查停止原因与已取得的结果。记录最后一轮已派发工作的归属。不能把耗尽记作完成了用户要求。数字 3 是测试设置。[有界执行待定项](../goal-shaping/archive/loom-agent/2026-11-23-initial/notes.md)

## A07 并行取两份报告，其中一份失败

在全新 S 给 A 两个有不同标记的测试报告源。U 发起普通交办“分别查询 X 和 Y 的报告，告诉我各自的结论，一项失败也要写原因”。让模型通过 Code Mode 请求两项，夹具先交回 Y。此时查询 Run，再交回 X。分别跑“X 成功”和“X 返回明确的终态错误”两组。用 U 领取最终答复，用获准的审查身份读取外层及子 ToolCall。

**通过。** 等待期间查得到 Y，Run 尚未交付最终汇总。两份结果由不同子调用接回同一外层。成功组汇总 X/Y 的不同标记，失败组准确指出 X 的原因并保留 Y 的结果。每组每一项在业务侧只执行一次，最终答复各一份。[并行与长等待](../spec/architecture/runtime.md#并行长等待和恢复)
