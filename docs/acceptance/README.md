## 身份和测试数据

| 身份 | 操作和可见范围 |
| --- | --- |
| 普通用户 U | 通过应用凭据在自己的 Session 交办、补充、取消、查历史和最终结果。测试部署可授权 U 从普通模板创建自己的 Agent。 |
| 另一用户 V | 在独立范围创建对照材料。需要越权验证时，以 U 的身份提供已知资源 ID，检查回应及业务结果。 |
| 测试管理员 | 准备模板、模型、插件、工具授权和测试范围。读取有权限的调用记录，用于复核 U 的操作。 |
| 测试来源与故障夹具 | CI、MCP、模型提供方和交付渠道使用各自的测试身份。延迟响应、切换 worker、暂停事务提交点、控制时钟只由测试部署操作。实际受测的提交、查询和恢复始终走 Loom 的正常入口。 |

每次实跑使用独立的测试范围或资源前缀，保存基线计数。准备两种模型配置。日常对话至少用一个真实可用的提供方跑通，观察回答和实际工具使用。需要精确复现截断、重复请求、模型尝试或竞态时，切换到可控提供方并记录配置。CI 夹具可以固定返回 300 行的报告，第 280 行含唯一的 `E421`。每次创建作业、查报告和最终送达都能在接收方按本次关联查询计数。这样可以独立发现“答对了但工具执行了两次”。

随用例提供两份固定输入。A02、C13 和 T07 可让 CI 返回[300 行日志](fixtures/t42.txt)的完整字节，作业名设为“发布验收”，将自动外置阈值调到低于样本大小。C14、C15 上传[失败截图](fixtures/report.png)，使用通用文件名，用户输入中省略预期用例名和错误码。给模型的材料和验收人手里的期望值分开传递。

## 怎样执行与取证

1. 记录测试实例地址、构建版本、API 契约版本、启用插件和本次执行标识。先按实例公开的契约核对方法、路由、请求体、鉴权及分页。文中的路径取自[候选 REST 目录](../design-review.md#rest)，动作名表达业务意图。待定操作由实现提供等价入口后再测。
2. 用普通身份实际发起请求。保存去掉凭据的请求、HTTP 状态、业务响应及对象 ID。按返回的 `event_id → delivery_id → run_id` 追踪，直到出现该 case 要求的等待、终态或交付结果。幂等重试复用原操作标识。独立新交办使用新的标识。列表有分页时读到本次基线或范围末尾。
3. 模型侧能力通过对话触发，再查实际 ModelCall 和 ToolCall。要求真实执行的 case 要能查到工具名、调用关系及特定返回值。涉及“执行零次/一次”的断言，按同一关联和基线查接收方计数。故障用例先确认已到指定时点，再注入故障，恢复后从同一个逻辑 API 地址读取原对象。
4. 启动时为每例记录观察截止时间。到期仍未得到结果，保存最后状态和已等时长。实例没有启动、测试身份缺失、夹具不能稳定制造所需故障或缺少核验入口时，记录受阻环节。有可用前置且观察到违反断言的结果，记录失败。已受理的 HTTP 状态、模型自述和设计文档都不足以判定通过。

每例各分支独立登记，可用一行保存一次结果。含模型、用户消息或外部日志的证据留在测试授权范围。

| 用例 / 分支 | 构建 / 执行标识 | 测试身份 | Event / Delivery / Run / Call | 期望与实测（含计数） | 证据引用 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 填用例编号及分支 | 填实例版本、本次标识 | 填角色 | 填实际返回的关联 | 填状态、结果和原因 | 填脱敏 HTTP 记录或夹具记录位置 | 待执行 / 通过 / 失败 / 受阻 |

普通模板的默认模型、可恢复的用户澄清和普通 Run 总预算按[第一期交付约定](../spec/goals/v1.md#phase-one-acceptance)验证。相应的两组模型配置、两个待澄清 Run 和三轮预算分别见[会话用例](conversation.md)。
