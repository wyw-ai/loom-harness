# Agent 与工具的 API 验收

验收人员用具名测试账号通过应用 API 创建资源、发起交办、读取执行证据。用有管理权的账号准备资源，用只获准访问指定 Agent 和 Session 的账号核查隔离。每次保留调用身份、资源 ID、有效修订、投递、Run、ModelCall、ToolCall 与可关联的外部请求记录。以下为待执行用例。

**接口约定**　文中的 HTTP 方法和路径采用[现有 REST 候选目录](../design-review.md#rest)，运行时按实例公布的契约填写参数、期望修订与凭据。统一设置资源路径 `/api/settings/{plugin}` 已确定，其方法与 schema 子路径仍是候选。模板发现、HOME 独立工具管理、文件应用及 MCP 连接更新均不另设假定路由。插件自有服务按有效接口目录访问。缺少需要的公开观察或操作入口时，记录该步未能验证。[对外契约](../spec/reference/contracts.md)

**发起交办和取证**　各用例使用独立测试数据，跨用例沿用的数据会单独说明。需要新会话时先 `POST /api/sessions`。每次交办先 `POST /api/events` 保存真人输入，再 `POST /api/events/{event_id}/deliveries` 以 `start_run` 投给目标。用 `GET /api/event-deliveries/{delivery_id}` 取得消费结果的 Run ID。用 `GET /api/runs/{id}` 看状态，`GET /api/runs/{id}/model-calls` 和 `GET /api/model-calls/{id}` 核对指定轮次的实际输入、目录和签名，`GET /api/runs/{id}/tool-calls` 核对父子调用、执行来源、版本和结果。工具执行次数与 CI/MCP 的业务请求数分开计数。仅有模型口头答复不足以通过。

## 真人可从应用 API 发起的用例

### T01　Agent 定义、绑定与并发修改

- **前置**　指定 HOME 已装入唯一的 `release`，其定义含名称、基础指令、主备模型、独立 Lua 工具、发布插件 Toolset 和 MCP 工具的稳定引用。两个管理客户端可编辑该 Agent。
- **请求**　`GET /api/agents` 和 `GET /api/agents/release` 对照预置定义。用 `PATCH /api/agents/release` 改简介并读回。两个客户端各读同一个新修订，甲带该修订更新主模型，乙随后仍带旧修订修改绑定，再读详情和 `GET /api/agents/release/tools`。
- **通过**　列表仅一个 `release`。详情与预置值一致，三类绑定均可解析。新简介和甲的主模型生效，乙看到修订冲突，原绑定保留。文件一致性与重启另见 T09。
- **反例**　旧请求成功覆盖主模型、凭相同名称生成第二个 Agent、只保存展开后的工具显示名，均判失败。[HOME 资源与生效规则](../spec/reference/home.md#apply)

### T02　从官方及第三方版本化模板创建

- **前置**　准备官方 `standard`、`creator` 和可见的第三方包 v1、v2。第三方版本分别声明可区分的基础指令，并引用一项受限管理工具。
- **请求**　通过实例公布的发现能力读取模板来源与版本，必要时用 `GET /api/plugins/{id}/versions/{version}` 核对 manifest。用 `POST /api/agents` 选定官方模板分别创建普通 Agent A 和创造者 C。选第三方 v1 创建 X，`PATCH /api/agents/{id}` 修改 X 的简介。用获准的包版本提交、启用操作发布 v2，再选 v2 创建 Y。分别查四者详情、有效工具和 X、Y 的版本来源。
- **通过**　返回调用者指定的四个独立 ID。X 保留 v1 指令和修改的简介，Y 采用 v2 指令。A 可回看自身资料，C 可用的管理能力与实际授权一致。独立 YAML 由 T09 核对。
- **反例**　发布 v2 回写 X，或受限账号单凭第三方模板列出管理工具就能实际管理目标，均判失败。[模板创建与授权](../spec/reference/home.md#agent-templates)

### T03　普通 Agent 的会话、收件与 Note

- **前置**　A 可读自己的会话 S。另一个 Agent B 与其材料仅对另一账号开放。记下 S 的 Run 和目标投递基线。
- **请求**　分别用 `POST /api/events` 创建带唯一标记的 E1、E2、E3，再各投递一次。E1 仅以 `attach` 投 S。E2 仅投给 A，选择无匹配消费规则的资料事件。E3 仅投给 B。向 S 发起一次交办，要求 A 自查定义、查 S 历史、查自身 Inbox，并在 S 调用 `write_note`、`search_notes`、`read_note`。查原三份投递、S 的 Run 列表、本次工具入参与返回。再以受限身份请求读取 E3。
- **通过**　自查标识为 A。S 历史含 E1，自身 Inbox 在三个标记中只命中 E2，两处均不返回 E3。查写 Note 返回的引用能读回原文。查询前后原投递的处理状态不变，没有查询引起的投递或额外 Run。
- **反例**　全局搜索泄露 E3 的正文、把投给 S 的资料算作直接投给 A，或查 Inbox 顺手消费 E2，均判失败。[普通 Agent 验收](../spec/goals/v1.md#agent-template-acceptance) · [Note 契约](../spec/reference/contracts.md#notes)

### T04　插件实例设置与 Agent 级配置隔离

- **前置**　同一版本插件启用为 P、Q，均声明 Agent 级正整数配置，并提供返回当前配置的只读工具。记录两个实例的有效 Settings 与修订。
- **请求**　用 `POST /api/agents` 创建两个 Agent，分别为 A/P、A/Q、B/P 设置 11、22、33。向 A、B 交办调用相应实例的工具，逐项打开 ToolCall。用 `GET /api/settings/{plugin}` 读两个实例。再以新 ID 创建 Agent，向目标 Q 传入不合 schema 的值，随后按该 ID 查详情与列表。
- **通过**　三次实际结果分别为 11、22、33，且来源实例正确。两个实例的通用设置维持原值。新建失败时可查校验原因，列表和详情均无半成品。
- **反例**　以包名索引导致 P、Q 串值，或后创建的 B 覆盖 A 的值，均判失败。[Agent 级 schema 与注入](../spec/reference/home.md#agent-templates)

### T05　MCP 包、连接与同名工具的授权

- **前置**　已登记一个不可变 MCP 包版本。实例 P 下有 `ci` 与 `docs`，实例 Q 也有 `ci`。两处 `ci` 提供同名 `search`，各服务可按测试标记查请求及收到的远端原名。Agent 仅获准 P 的 `search`。
- **请求**　`GET /api/plugins/{id}/versions/{version}` 查包，查询实例设置。经插件公布的连接服务分别读回地址与凭据引用。用同一服务仅修改 P/ci 的地址并完成发现。将两项 `search` 加入同一集合，给 Agent 新交办调用获准项。再让有权的 Agent 调 P/docs。查实际 ModelCall、ToolCall 与各端业务请求。
- **通过**　能分别核对包版本、实例设置、两条连接的地址与凭据引用。首个 Agent 的目录仅出现 P/ci 获准项的 ID 和签名。其请求只到 P/ci 新地址且远端原名为 `search`。P/docs 仍走原地址。撤权瞬间另见 T11。
- **反例**　Q/ci 的工具签名泄露、工具按远端短名错派、修改 P/ci 时同时改写 P/docs 或不可变包，均判失败。[插件包与实例](../spec/reference/home.md#packages) · [工具来源](../spec/reference/tool-sources.md)

### T06　混合集合、父子调用与唯一入口

- **前置**　发布集合含 `home.check_release_tag` 与 CI 的 `get_report`。另备可单独绑定且被两个集合共同引用的默认内置成员，以及一项显式直接调用的成员。后端可区分发现请求和业务调用。
- **请求**　先让发布 Agent 只绑定发布集合，交办以一段 Code Mode 程序检查标签并取构建 B42 的报告，查看本轮目录、父子调用及下一次模型输入。再添加重叠绑定及直接成员，分别经允许入口调用。尝试通过原生入口调默认成员、通过 Code Mode 调直接成员。最后 `PATCH /api/agents/{id}` 移除一条重复绑定并交办新一轮。
- **通过**　第一次目录只有这两项业务工具。一次外层调用关联两个不同 ID 的子调用，可分别查本地代码和远端连接版本、结果。CI 仅收到一次 `tools/call`，父程序取得两个子结果，模型取得外层汇总。第二次每个获准 Tool ID 仅出现一次，两条错误入口的业务执行数均为零。移除一条绑定后仍可经剩余绑定调用。
- **反例**　把同一成员同时暴露为原生与 Code Mode 入口、返回汇总却查不到两个子调用、移除一个集合导致其他有效绑定也失效，均判失败。[混合 Toolset](../spec/reference/tool-sources.md#mixed-toolset)

### T07　创造者从 CI Note 开发、启用并实调

- **前置**　测试 CI 执行一次，产生自动外置的 300 行日志。正文第 280 行含 `E421`，描述不含该码。C 获准读该 Session 的 Note、阅读版本指南、管理自己的绑定与指定插件。另备无目标管理授权的创造者。
- **请求**　真人向 C 交办查生效指南、定位日志 Note、编写只读错误码提取工具、提交版本、在测试范围启用并绑定给自己。要求 C 在下一次有效目录中用原 `note_ref` 调用新工具，再读取该轮 ModelCall 和 ToolCall。随后交办 C 停用并从新一轮查询目录。分别让普通 A 申请安装、无目标权限的创造者改别人绑定及越范围启用，管理账号对照操作前后的资源。
- **通过**　记录显示 C 实际完成创作和启用，新工具调用指向获准实例与新版本、原 Note 引用及返回的 `E421`。CI 实际仍只执行一次。停用后新目录撤下入口，历史 ToolCall 仍可读。三项越权操作均未生效，目标的有效修订、绑定、启用状态保持原值。停用后旧绑定的在途派发见 T11。
- **反例**　仅回复错误码、由真人代为安装或直接调用外部脚本，都不能证明 C 完成了实调。自行编写插件后获得额外管理权限也判失败。[创造者验收](../spec/goals/v1.md#agent-template-acceptance) · [Note 原文回读](../spec/reference/contracts.md#notes)

### T08　Lua 插件的公开扩展与实际上下文

- **前置**　准备同一插件契约下可启用的第三方 Lua 测试包，声明可辨认的 REST 响应、配置字段、prompt section 和事件订阅。另有可单独替换推理触发或输入构建的测试插件。
- **请求**　先以默认实现完成一次交办。经插件管理接口启用测试包，按实例实际公布的路由调用它注册的服务。经 `/api/settings/{plugin}` 更新并读回测试值。提交其订阅的测试 Event，核查订阅结果。再交办调用该插件工具，读取实际返回及 ModelCall 中相应 section。分别只替换推理触发、只替换输入构建，使用相同输入再交办并比较结果。
- **通过**　可从接口响应、订阅结果、ToolCall 和实际模型输入核对声明的能力与生效值。单独替换触发时仍有原构建提供的内容，单独替换构建时仍由原触发条件发起。测试包与默认提供方均可工作。
- **反例**　Settings 已保存但处理函数仍读旧值、只有预览含 section 或两种扩展必须同时替换才可运行，均判失败。本期不以 Run 内按需开启工具集、特定示例工具名或 Skill 接入作为判据。[插件与上下文](../spec/reference/contracts.md#插件工具与上下文) · [开放能力](../spec/goals/v1.md#开放能力)

## 需要受控夹具或故障注入的用例

以下仍从应用 API 交办及取证。夹具负责检查 HOME 文件、让远端按指定次序返回、在派发前暂停、重启宿主或更换 worker。T06、T07 的拒绝用例若因模型未发出指定请求而无法验证，可让受控模型适配器返回该工具请求，沿真实授权和派发路径复测。夹具日志用于核对实际业务调用次数。不得拿本地改库代替公开接口的读回。

### T09　HOME 文件、重启与独立 Lua 修订

- **前置**　沿用 T01 的 HOME、T02 创建的 X/Y，标签工具初版仅接受正式标签。记录初始有效修订，夹具可检查文件与触发实现支持的应用动作。
- **请求**　复读 `GET /api/agents/release` 并核对同一 HOME 的 `agents/release/agent.yaml`、X 与 Y 各自文件。重启后再查。交办检查 `v1.2.3-rc.1`，修改 `tools/check_release_tag/` 的定义和 Lua 使其接受预发布标签，成功应用后以同一 Tool ID 重试。再仅改处理函数为另一份可辨别的有效实现，应用并观察新调用。最后提交编译失败的 Lua、读应用诊断并再调用一次。
- **通过**　文件与 API 中的 ID、简介、有效定义相符，重启仍可按同一修订读回。X/Y 的文件独立。标签判断由拒绝变为接受。仅改代码也产生新修订。编译失败后能区分待应用内容、错误与最近有效修订，新调用继续采用最近成功的代码。
- **反例**　坏代码替换有效版本、失败后 Tool ID 消失，或旧调用记录被新修订覆盖，均判失败。[HOME 应用](../spec/reference/home.md#apply) · [HOME 验收](../spec/goals/v1.md#home-acceptance)

### T10　MCP 分页刷新、修订竞态与成员消失

- **前置**　CI 有多页工具清单和已成功登记的基线，所在集合还含可调用的本地标签工具。夹具能控制页响应顺序、连接修订以及连通性。
- **请求**　触发一次发现并让末页失败。读来源诊断、当前工具及对应目录。随后挂起旧连接修订的刷新，修改连接并完成新修订刷新，再释放旧响应。分别在完整清单移除远端成员、连接失联两种条件下，交办调用消失或失联的成员以及本地成员。
- **通过**　末页失败可查原因，基线仍可追查且未发布部分目录。迟到旧响应未覆盖新修订。失效成员停止派发，有权管理员可查原因，两个条件下本地工具均可用。
- **反例**　看到前页新增成员就提前上线、复活旧清单、任一远端失效导致整个集合停用，均判失败。[来源装载与目录快照](../spec/reference/tool-sources.md#目录快照与派发)

### T11　快照后撤权、停用或改变签名

- **前置**　沿用 T05 的同名来源与 T07 的提取工具。夹具能暂停在 ModelCall 已固定目录、业务工具尚未派发的时点，并保留旧请求和外部计数。
- **请求**　分别发起三次独立交办并在该处暂停。第一组撤回获准 P/ci 的授权。第二组停用 C 的提取插件。第三组使宿主完成发现并登记 CI 工具的新签名。第三组更换 worker。释放各自已按旧目录生成的请求，读历史 ModelCall 与 ToolCall 或拒绝记录，再交办新一轮查询最新目录。
- **通过**　撤权组两个远端业务请求数均为零。停用组旧绑定的实际执行数为零。签名组返回原绑定失效且 CI 收到零次调用。新一轮反映撤权、停用或新签名。接手者仍能查回旧目录、签名及原调用引用的代码或连接修订。
- **反例**　沿旧绑定派发一次、把旧调用静默改投另一实例，或用新签名覆盖历史输入，均判失败。[派发复核与跨 worker 恢复](../spec/reference/tool-sources.md#目录快照与派发)

### T12　CI 已受理后的换 worker 与回执恢复

- **前置**　发布集合包含获准提交 CI 的工具，交办要求取得最终报告。CI 夹具记录收到的请求、原参数、稳定键及实际创建的作业。为每个分支另开 Run。
- **请求**　经 Code Mode 交办提交一次。对照组先保存 CI 返回的作业号，再更新 Agent 定义和 MCP 实例配置并换 worker，随后让 CI 送最终报告。另三组让 CI 建好作业后丢弃首个受理回执再换 worker，依次配置远端支持按派发前保存的键查询、只保证有效期内同键同参重交、两者均不可用或保证已过期。最后一组显式启用 Goal。先查原 Run，再给待核实组送可关联的迟到受理回执。各组重复投递最终报告并查原父子调用及后续 ModelCall。
- **通过**　对照组凭旧作业号接回原调用，只提交一次。能按受理时 Agent 修订、原 ModelCall 目录及原 ToolCall 的执行者、版本和配置回查。按键查询组只提交一次。允许重交组对原绑定发出相同键及原参数，远端始终只有一个作业。无安全依据组在迟到回执之前显示结果待核实，无第二次提交。找回作业号后仍待最终报告。重复回执最多触发一次报告分析，均关联原 CI 子调用。
- **反例**　重跑整段 Code Mode 程序、超时记为测试失败、Goal 自动补提作业或收到作业号就完成交付，均判失败。[首回执丢失验收](../spec/goals/v1.md#ci-lost-receipt-acceptance) · [混合集合恢复](../spec/goals/v1.md#mixed-toolset-acceptance)
