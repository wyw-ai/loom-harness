# 普通交办与 Goal 主动续跑

交办方发起一次工作时，可以直接要求一个结果，也可以显式启用官方 Goal 插件，要求 Agent 持续推进到指定目标。两种交办都由原 Run 承担，沿用同一套等待、恢复和交付机制。

## 普通交办怎样结束

模型正常给出最终答复、本轮没有请求工具，且交办所需结果都已就绪时，普通 Run 按约定校验和交付。例如，用户要求汇总两份报告，一份报告尚在生成时，宿主保存作业标识并释放 worker。回执到达后原 Run 接续，取得两份报告或各自明确的失败原因后才能交付汇总。若只在失败时通知，检查成功并保存结果即可结束。

## 什么情况下持续追求目标

交办方在发起 Run 时显式启用 Goal，并说明要达到的结果，例如“修复这条回归，用同一用例复测确认通过”。模型完成一次修改后，如果复测仍失败，Goal 插件可让原 Run 带着失败证据再推理，决定下一步。如果复测任务还在运行，宿主等待此次调用的回执。作业完成后，模型查看实际结果，有证据支持目标已达成时，显式标记目标完成。宿主接着按原约定交付。

Goal 只对启用它的这一项交办生效。同一 Session 后续发起的交办仍可走普通流程。宿主处理已登记的等待、取消、预算和最终交付。取消生效或预算耗尽会停止主动续跑，停止原因可与目标达成区分。独立判断业务结果是否正确的 outcome 验收插件继续暂缓。

## 下一次推理看到什么

宿主采纳 Goal 插件的主动续跑请求时，在原 Run 内按已有的推理请求机制记录本次决定，由这条内部 Event 触发本轮输入构建。这条内部请求不经过收件箱，也不创建新的 EventDelivery。

Goal 有效期间，每次为交办发起主模型推理，构建器都从原 Run 取得当轮有效的完整目标、完成条件和已生效的用户约束。已结束步骤的历史可以使用摘要，未决调用保留标识和状态。若 CI 可能已创建作业而作业号尚未取回，压缩后仍保留待核实的原 ToolCall，Goal 不能据此新建一次提交。[首个受理回执丢失时的处理](../2026-11-23-initial/tools.md#lost-acceptance-receipt)

当前目标与完成条件必须能在实际输入中直接读到，本轮所需的证据保留原文或可读取的引用。只有触发原因是 Goal 主动续跑时，才在所选历史之后追加内部续跑说明。

续跑说明在模型输入中使用 `user` 角色，并标明来源为 `goal`。这条说明仅随本次 ModelCall 的实际输入留档，不作为用户聊天写入 Session，也不单独发布说明 Event。复测回执若满足原 Run 的等待，可以按该回执作出一次推理决定。模型同时看到复测报告和有效目标，宿主无需为同一次唤醒再发起 Goal 续跑或追加续跑说明。

## 压缩期间目标发生变化

若用户在压缩旧历史时将“修复并复测”改为“只读分析”，宿主在采用摘要前核对已受理的改动。旧决定失效时，按新约束重新组装。若取消已生效，停止原定推理。摘要就绪只恢复仍有效的输入构建，沿用原决定和触发原因。派发工具或交付答复前，宿主再次核对生效的约束。

压缩失败时，如果原文仍能放入模型窗口，可以回退使用原文。若错误不可恢复或重试耗尽，且已无法构建有效输入，宿主停止自动续跑并记录具体原因。目标完成仍需模型依据业务证据显式标记。
