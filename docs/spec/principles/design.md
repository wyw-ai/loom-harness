# 设计原则

## 让交办有明确的归属和结束条件

Session 提供可持续投递的地址；一次 Run 承担一项有结束条件的交办。业务安排决定何时需要通知谁。Agent、受控资源和 worker 可以分开部署。Run 所需的等待与进度由宿主保存，客户断线或 worker 更换后仍可接续同一次工作。

## 明确事件、投递和调用各自承诺什么

Event 表达已经发生的事实。投递表达某个目标应收到这份事实和相应意图。推理触发与输入组装分别回答“是否需要模型”和“模型要看到什么”。模型或工具调用有明确的执行者、结果和关联标识。根据这些关系，系统可以单独留档、观察、等待，也可以在需要时发起推理。一次工具结果到达时，先核对它属于哪个调用。

## 保留材料的来源，让上下文按需组装

每轮模型输入应能说明使用了哪些材料。分支、压缩与上下文编辑按新的选材或派生结果表达，原始事实及其归属保持可追溯。系统指令的长期约束来自 Agent 和生效的 section。工具与 Skill 通过目录或简介先暴露用途，再按需提供详细说明和内容。外部应用负责决定哪些工作区材料应送入 harness。

## 官方与第三方共用扩展机制

Rust 宿主维护执行与状态，插件在公开的扩展点参与。事件订阅允许多个消费者独立处理同一事实，模型调用和单个工具调用各自绑定一个执行实现。工具接入方式可扩展，内置工具、Lua 工具和 MCP 工具遵守相同的 Code Mode 默认与显式直接调用约定。

## 在授予的范围内管理资源

由用户通过 REST 管理的资源，也可在获得授权后由 Agent 工具管理。两类入口对同一操作采用相同的资源语义与权限约束。写入配置、实际装配和本轮模型请求所见应可区分。发起、补充或取消进行中的工作优先通过事件投递，资源管理使用对应服务。插件调用所需配置与权限由宿主提供。

这些原则用于判断后续实现和扩展是否仍能满足[首版目标](../goals/v1.md)。具体对象关系和恢复路径见[云端执行架构](../architecture/runtime.md)。
