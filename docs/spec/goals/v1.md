# 首版目标与验收

loom-harness 为云端 Agent 提供上下文和运行管理。调用方可以定义 Agent，将交办或材料投给它，在并行调用和长时间等待后取得约定的结果。官方及第三方插件可以扩展模型、工具、上下文和投递行为。

以下场景定义第一期的验收标准。仓库提供可运行的 Rust 服务、普通用户的 HTTP 验收脚本和故障夹具。[启动服务](../../../README.md) · [本机实跑结果](../../acceptance/results-v1.md)

<a id="phase-one-acceptance"></a>

## 第一期怎样算完成

第一期交付一个可由上层应用实际调用的 Agent 服务。由 Codex 模拟用户，优先在本机测试实例通过 HTTP API 创建普通 Agent、发起交办、查询结果并在重连后继续对话。普通对话至少用一个真实模型提供方走通。需要复现回执丢失、重复消费、模型故障或换 worker 的场景时，用测试夹具控制故障时点，再通过同一 API 核实恢复结果。

代表用例是让 Agent 查 T42 的失败报告并回答错误码。用户重连后在同一 Session 追问行号，第二个 Run 能沿原报告找到第 280 行的 `E421`，第一个 Run 保持完成，CI 侧仍只有一次报告查询。[会话用例 A02](../../acceptance/conversation.md)

| 核对范围 | 用例 |
| --- | --- |
| 模板创建后的首问、追问、补充、取消和并行查询 | [普通会话 A01–A07](../../acceptance/conversation.md) |
| 模型与上下文、图片与结构化交付、分支、压缩、Goal、推荐和 Note | [上下文与模型 C01–C15](../../acceptance/context-and-goal.md) |
| HOME 修订、角色与授权、MCP 与自定义 Lua、混合工具集、创造者实调 | [Agent 与工具 T01–T12](../../acceptance/agent-and-tools.md) |
| 投递与审批、外部交付、本地与 Redis 总线重送、执行池与插件订阅 | [投递与恢复 R01–R13](../../acceptance/recovery-and-dispatch.md) |

已确认且适用的用例逐项实跑通过，才满足一期验收。每项保存构建标识、测试身份、脱敏请求与响应，以及支持判据的 Event、Delivery、Run 或调用记录。涉及外部副作用时，以接收方计数核对实际执行次数。A04–A06 采用三个可以独立验证的实现约定。Agent 可继承部署默认模型，缺少可用模型时 Run 以明确原因结束。用户补充缺失资料时用 Run 和问题 ID 恢复原等待。普通交办与 Goal 均受每个 Run 的轮数上限约束。[执行说明与结果记录格式](../../acceptance/README.md)

## 单次交办能持续到履约

| 场景 | 可观察的结果 |
| --- | --- |
| 普通交办要求根据已提供的报告回答问题 | 模型正常返回最终答复，本轮没有工具请求，交付所需的材料和结果都已齐备。宿主按原交付约定返回答复并结束 Run。 |
| 在一个 Session 中要求 Agent 查两份报告并综合结论 | 同一 Run 可以多次调用模型和工具。先返回的子调用交回实际调用者，另一项仍可继续。最终结论包含两项结果或各自明确的失败原因。 |
| 普通交办要求交付最终报告，工具先返回作业号，期间 worker 重启 | 原 Run 登记等待并释放 worker，稍后按调用与作业标识接回报告。这条路径无需启用 Goal。重复回执只能推进同一次等待一次。对外部动作结果未知时，可以查到其未决状态。 |
| 原交办约定“仅在失败时通知” | 检查成功并记录结果后即可完成。需要通知时，系统保存答复和目标，按约定的交付条件结束。发送重试沿用原答复。 |
| 用户给已有交办补充要求或请求取消 | 外部通过事件向所属 Session 投递并关联原 Run。已受理的补充可参与后续判断；接受取消后停止新派发，迟到回执仍可追溯到原调用。 |

<a id="ci-lost-receipt-acceptance"></a>

### CI 已创建作业，首个受理回执丢失后更换 worker

交办要求取得最终测试报告并分析失败原因。让 CI 先创建作业 `T42`，丢弃携带作业号的首个回执，随即更换 worker。用 CI 侧记录确认作业已创建，接手的 worker 读取原 ToolCall 的派发记录时看不到 `T42`。分别按以下三种工具能力验收。

| CI 的能力 | 可观察的结果 |
| --- | --- |
| 可按提交前保存并发送的稳定键 `K` 查询 | 新 worker 用 `K` 查回 `T42` 并关联到原 ToolCall。CI 只收到一次提交。 |
| 不可按键查询，但保证有效期内同键重提会返回原作业号 | 在有效期内向 CI 重提原参数，前后两次请求携带相同的 `K`。新 worker 取得 `T42` 并关联到原 ToolCall。CI 侧实际只创建一个作业。 |
| 无法按键查询，并且服务没有幂等保证或其有效期已过 | 调用方能看到“CI 可能已受理，作业号待核实”。即使启用 Goal，也没有第二次提交，没有将超时记为测试失败。随后若收到能关联到原 ToolCall 的迟到受理回执，原 Run 继续等 `T42` 的报告。 |

在找回 `T42` 的分支中，检查受理后 Run 仍在等待。让 CI 重复投递同一份失败报告，原 Run 只登记一次由工具回执触发的报告分析，CI 侧始终只有一个作业。

## 显式启用 Goal 的交办

| 场景 | 可观察的结果 |
| --- | --- |
| 交办时启用官方 Goal 插件，要求“迁完 20 个模块，并跑通全量测试”。模型在迁完 14 个后给出阶段总结，此时没有在途工具 | 首轮总结记入原 Run 的进度。插件请求在原 Run 中继续推理，无需用户再发消息。模型核对 20 个模块的迁移结果和全量测试通过的报告后，显式标记 Goal 完成。宿主按原约定对外交付最终答复。 |
| 追查迁完第 14 个模块后如何续跑 | 原 Run 中可查到持久保存的推理请求，原因是 Goal 续跑。重放同一次续跑决定时仍可查到同一个请求。此次续跑没有新增 EventDelivery 或 Inbox 收件，聊天界面也没有新增用户发言。 |
| 使用已压缩的历史构建这次续跑输入，再重试同一请求 | 实际发给模型的 message list 仍包含当前迁移目标和“20 个模块全部迁完、全量测试通过”的完成条件。所选历史之后有一条内部续跑说明，角色为 `user`，来源标为 `goal`。重试后这条说明仍只出现一次。后续调用按各自的推理原因组装输入，旧说明不会随历史或摘要累积。 |
| Goal 运行期间，下一步需要等测试作业返回 | 沿用 Run 的等待记录。期间不因 Goal 仍在进行而反复调用模型。若接受取消或耗尽约定预算，停止自动推进，保留实际停止原因。 |
| 同一迁移交办已提交全量测试 T42。等待期间历史被压缩，随后同一份失败回执到达两次 | 回执归入 T42。原 Run 只登记一次分析失败的主推理，触发原因为工具回执满足等待。实际发给模型的输入包含当前迁移目标、完成条件和失败报告或可回读的引用。该轮的 Goal 主动续跑说明为 0 条，T42 只提交过一次。 |
| 为分析 T42 的失败报告而压缩历史时，用户收紧要求为“只分析，别重跑”或取消交办，随后旧摘要就绪 | 收紧要求生效后，新一轮实际输入包含该限制，旧的重跑建议不会被派发。若取消已生效，失败回执仍可查，迟到或重复的摘要不会重新启动原 Run。 |
| 组装 Goal 所需输入时发生不可恢复的压缩错误 | 原 Run 记录可查询的失败原因，停止针对同一错误的主动重试。 |

## 输入框推荐

Agent 已在 Session 中答复“修改已提交到本地，尚未推送”。以这条答复为起点，分别验收以下场景。

| 场景 | 可观察的结果 |
| --- | --- |
| 输入框显示推荐“推到远端”，用户采纳后改成“先看差异”，再发送 | 采纳和编辑期间，消息历史及收件记录保持原状。发送后新增一条 EventDelivery，关联的用户消息为“先看差异”。 |
| 基于版本 `v18` 请求推荐。暂缓模型响应，待 Session 受理用户发来的“先别推”后，再让模型返回“把刚才这个提交推到 origin/main 吧。” | 服务端丢弃旧采样结果。另将已从服务端发出的 `v18` 响应延迟到用户点击发送后才送达，客户端也丢弃它，保留当前输入框内容。两种时序下，新增投递各只有“先别推”对应的一条，推荐产生的 ToolCall 和 Run 均为 0，远端仓库未收到推送。 |
| 同一 Session 中有一份仅 Agent 可读的工具报告，已有摘要引用了该报告 | 核对实际出站的采样输入，私有报告及其受限内容均未进入输入。若模型仍请求调用推送工具，宿主结束采样，工具执行次数为 0，调用方收不到这条工具请求作为推荐。 |

## 用户可指定模型、图片输入和最终结果

| 目标 | 验收时检查什么 |
| --- | --- |
| 模型选择 | 给 Agent 配置可用模型，发起一次交办。从该轮调用记录能核实实际使用的模型。 |
| 故障切换 | 配置兼容的备选并让首选模型临时不可用。原 Run 按配置继续，主备尝试可区分；已经派发的工具仍按原调用处理。没有满足本轮能力要求的备选时，调用方能取得失败原因。 |
| 用户图片输入 | 用户提交文字和图片。检查提供方收到的实际请求中包含可解析的图像内容；图片引用不可读时可查到失败原因。 |
| 结构化结果交付 | 调用方随交办约定最终结果的结构。宿主校验准备交付的最终值，调用方取得满足约束的结果或明确的校验失败。中间工具的返回格式按该工具自己的契约处理。 |

联动验收可使用一张带已知用例名和错误码的失败截图，要求输出两个指定字段。首选模型临时不可用后，支持图片的备选应读到原图，交付值通过约定结构校验，并能追溯同一 Run 的两次尝试。模型选择的配置字段、允许切换的错误分类与具体重试次数仍待接口评审。

<a id="notes-acceptance"></a>

## Note 的检索与日志回读

让外部工具返回一份 300 行、达到自动外置条件的日志。仅正文第 280 行含错误码 `E421`。使用“发布验收”作为作业名，使自动生成的描述含“发布验收”且不含 `E421`。分别从 Session 历史和原工具结果 Event 打开这项结果，再更换 worker。[Note 契约](../reference/contracts.md#notes)

| 检查 | 可观察的结果 |
| --- | --- |
| 在同一可见范围先后用 `write_note` 写两份带不同描述的 Note，再省略关键词列出 | 两次写入均取得可回读的引用。列表按 `created_at` 从新到旧返回元数据，后写的排在先写的前面。 |
| 比较两个入口展示的原工具回执 | 从 Session 历史和原结果 Event 都能找到相同的 ToolCall、日志内容块、预览和自动生成的 `note_ref`。读取这个引用得到原日志版本。 |
| 在可见 Note 中搜索 `E421`，再搜索“发布验收” | 前者查不到这份 Note，后者的元数据里包含这份 Note 的引用。两次搜索均不返回正文。 |
| 换 worker 后按原引用读取 | 给足读取预算，省略范围可读回全部 300 行，顺序、内容与原日志一致。请求第 280 至 280 行只返回含 `E421` 的那一行。只给结束行 2 时返回前两行，只给起始行 299 时返回最后两行。文件头不计入正文。 |
| 限制本次模型预算后再读全文，并核对执行记录 | 全文容不下时，调用方得到明确的超限结果、正文大小和总行数，随后可按原引用缩小范围。读取过程产生的新 Note 为零，外部工具始终只执行一次。 |

## 上下文与事件投递

| 场景 | 可观察的结果 |
| --- | --- |
| 同一条构建报告既要给归档 Session 留档，又要请值班 Agent 排查 | 两次投递可独立查询并引用同一 Event。留档只增加材料；交办才建立 Run。即时、定时和条件投递可通过同一安排机制配置。用户经 REST、获授权的 Agent 经工具管理同一份安排；Lua 规则可以决定是否发送、内容和目标。 |
| 历史逐步超出模型输入预算 | 官方压缩能力使所选历史可以压缩后参与模型调用。可以检查压缩覆盖的历史和本次实际采用的内容。当前交办、未决工具状态以及原事件仍可追溯。 |
| 从已有会话某个历史位置创建分支 | 官方 branch 插件创建可独立继续的子 Session。能核对来源和切点，从子会话继续交办。原会话的活动 Run、待完成工具调用以及结果仍由原所有者接回。 |
| 工具集注册了一段说明，后续刷新或撤出 | Session 启动时按适用范围组装 section，后续模型调用看到最新有效内容。每轮 message list 可按扩展策略选择、排序、编辑材料。 |

<a id="event-distribution-acceptance"></a>

### 本地与 Redis 总线的分发中断与重复送达

准备一个等待 CI 最终报告的 Run。让处理报告的运行时订阅和一个独立的审计订阅消费同一事件，记录其 `event_id`。默认本地总线在同一 HOME 上验证服务重启及多个 worker 接手。Redis Streams 通过相同订阅接口验证同样的故障边界。[事件分发约定](../architecture/runtime.md#event-distribution)

| 故障注入 | 可观察的结果 |
| --- | --- |
| 宿主已将报告事实和发件箱记录一起提交，默认模式在首次本地消费前停机，Redis 模式在首次写入 Stream 前停机 | 重启后按发件箱记录分发原 `event_id`。持久事件中这份报告只有一条。运行时订阅满足原 Run 的等待并登记一次下一步，审计订阅也独立记录一次报告。 |
| 运行时订阅已提交等待满足和下一步，在本地待确认条目清除前或 Redis 的 `XACK` 前停机。让审计订阅独立处理，再将原事件重新交给运行时订阅 | 两个订阅按各自的持久记录识别同一事件。业务库仍只有一份报告事实，原 Run 对该等待只登记一次下一步，审计记录也只有一份。 |

<a id="worker-pool-acceptance"></a>

### 单进程与多 worker 执行池

| 场景 | 可观察的结果 |
| --- | --- |
| 默认启动一个 `loom-harness` 进程，提交 A、B 两项独立交办，让 A 等待 CI 报告 | 客户端从同一个逻辑 API 提交和查询两项交办。默认一个 worker 可以在报告到达前执行 B 的就绪步骤。A 的等待与 ToolCall 仍可查，收到有效报告后继续原 Run。 |
| 以同一程序分开运行 API 与执行职责，增加多个 worker。让两项独立工作同时就绪，并让两个 worker 竞争处理同一 Run、同一状态版本的步骤，再重复送达唤醒它的事件 | 独立 Run 的步骤可以并行。竞争与重送只提交一次对该 Run 的有效推进。其他独立订阅仍按各自进度处理该事实。客户端沿用原 API 和 Run 标识。 |

**负载对照。** 固定交办内容、并发请求数、模型与 CI 的响应时延，分别以 1、2、4 个 worker 运行相同负载。每组记录两项指标。吞吐量为每秒成功提交的独立就绪 Run 步数，同一次推进经竞争或重送只计一次。排队时延从宿主接纳使等待满足的回执起算，到对应下一步实际开始执行为止，报告其第 95 百分位（p95）。用三组实测值评价扩容效果，增长倍数随负载和瓶颈而定。[执行与部署约定](../architecture/runtime.md#worker-pool)

<a id="home-acceptance"></a>

## HOME、Agent 定义与工具装载

以发布 Agent `release` 为例，验证部署者能从 HOME 定义资源、通过 REST 读写同一资源，并从运行记录查到实际生效的版本。下表用于验收后续实现。示例资源名和 YAML 字段见 [HOME 目录与资源定义](../reference/home.md)。

| 场景 | 可观察的结果 |
| --- | --- |
| 在指定 HOME 的 `agents/release/agent.yaml` 声明名称、基础指令、主备模型和工具引用，启动服务，再通过 REST 修改简介 | Agent 列表中只有一个 `release`。按 ID 读回的定义与文件相符。REST 更新后，同一文件反映新简介，重启后可读回同一 ID、新简介及对应的生效修订。 |
| 让 `release` 引用 HOME 独立工具、发布插件登记的工具集和 MCP 工具 | 读回的 Agent 定义保存各绑定的稳定引用。各成员如何出现在当轮目录、撤权后实际派发几次，见[混合 Toolset 验收](#mixed-toolset-acceptance)。 |
| 修改 `tools/check_release_tag/` 下的 `tool.yaml` 和所引用的 Lua，使规则接受预发布标签，应用后再提交一份有语法错误的脚本 | 有效变更作为一个修订生效，用同一个工具 ID 测试 `v1.2.3-rc.1` 可观察到新规则。第二次应用能查到待应用内容、错误原因及上次生效修订，已有工具仍按上次规则执行。 |
| 两个管理客户端从同一 Agent 修订出发，一个先更新主模型，另一个仍以旧修订提交工具绑定 | 后一次更新得到修订冲突，读回的 Agent 仍指向先前已成功更新的主模型。 |
| 在 `packages/` 安装一个 MCP 包版本，在 `plugins/` 配置一个实例及 `ci`、`docs` 两条连接，再修改 `ci` 的地址 | 可分别读回包版本、实例的生效设置以及两条连接各自的地址和凭据引用。重新发现 `ci` 后，其工具走新地址，`docs` 的工具仍走原连接。 |
| 原 Run 已派发 CI 作业，随后更新 Agent 定义和 MCP 实例配置，再换 worker 接收报告 | 接手的 worker 能读回 Run 受理时的 Agent 修订、原 ModelCall 实际使用的工具目录，以及原 ToolCall 的执行者、工具版本和生效配置。报告按原作业标识回到该调用，CI 作业只提交一次。 |

<a id="mixed-toolset-acceptance"></a>

## 混合 Toolset 的装配、派发与恢复

让部署者把本地 Lua 标签检查和 MCP 连接 `ci` 提供的 `get_report` 编入同一个发布检查工具集。以下六个场景用于验收后续实现。本次覆盖 MCP 和自定义 Lua 工具，Skill 接入暂缓。[混合 Toolset 定义与绑定](../reference/tool-sources.md#mixed-toolset)

| 场景 | 可观察的结果 |
| --- | --- |
| 发布 Agent 只绑定这个集合，用一段 Code Mode 程序先检查标签，再读取 CI 报告 | 本轮有两个业务工具。标签检查调用本地 Lua，CI 只收到一次对 `get_report` 的调用。记录中有一个外层调用和两个 ID 不同的子 ToolCall，两个子调用都能查到各自的来源和版本，并指向同一父调用。程序收到两个子结果，模型收到外层汇总。 |
| 同一工具被单独绑定，又被两个集合引用，其中一个集合还包含显式直接调用的成员 | 每个获准的 Tool ID 在本轮目录中只出现一次。默认成员经 Code Mode 调用，直接成员经模型原生入口调用。尝试走另一入口时执行次数为零。移除一条绑定后，其他有效绑定仍可提供该工具。 |
| 两个 MCP 实例各有一个名为 `ci` 的连接，两端都提供 `search`。把两项加入同一集合，仅授权其中一端 | 当轮目录只展示获准成员的 ID 和签名，正常调用只到获准的连接。在另一轮生成目录后、派发前撤回该授权，再用旧目录请求，两个远端收到的请求均为零。 |
| 同一连接的工具清单有多页。先让末页失败，再让旧连接修订的刷新晚于新修订返回，最后让已登记的远端成员消失或连接失联 | 末页失败可查原因，上次成功的清单仍可查，未发布部分结果。迟到的旧刷新不能覆盖新目录。失效的远端成员停止派发，获准的管理员可查原因，集合内的本地标签工具仍可调用。 |
| 仅更新本地 Lua 代码并成功应用，再提交编译失败的修改。同时让宿主发现 CI 工具的签名已变，然后更换 worker | 按 [HOME 修订验收](#home-acceptance)核对本地工具，新调用仍使用最近成功应用的代码。接手者能查回旧 ModelCall 的目录、签名及原 ToolCall 对应的代码或连接修订。按旧签名请求派发时得到绑定失效，远端调用次数为零。下一轮可读到新签名。 |
| 给发布检查集合加入获准提交流水线作业的工具，经 Code Mode 调用。CI 已受理，首个回执丢失后更换 worker | 按[首个受理回执丢失验收](#ci-lost-receipt-acceptance)核对三种恢复分支。恢复针对原来的 CI 子调用。缺少查询或安全重提依据时保留“结果待核实”，整段程序不重跑。可关联的迟到或重复回执最多满足原等待一次。 |

<a id="agent-template-acceptance"></a>

## Agent 模板、权限与插件实调

使用首版的 `standard`、`creator` 和一个第三方版本化包提供的模板进行验收。为普通 Agent 与创造者分别设置实际授权；创造者可管理自己的绑定与指定的测试插件范围。[模板、插件声明与创建示例](../reference/home.md#agent-templates)

| 场景 | 可观察的结果 |
| --- | --- |
| 从第三方包的 v1 模板创建 A，再发布修改了基础指令的 v2 模板并创建 B | 每个 Agent 使用创建时指定的 ID，得到独立的 `agent.yaml`。A 保留 v1 生成的指令和自己的修改，B 采用 v2。第三方模板中列出的管理工具仍受创建者与目标的权限约束。 |
| 在普通 Agent A 的 Session S 中，分别将 E1 仅投给 S、E2 仅投给 A 的 Inbox，E3 仅投给无权访问的另一个 Agent | 自查返回 A 的定义。在 S 的历史可找到仅作会话资料的 E1；查 A 自身 Inbox 只命中直接投给 A 的 E2。两处都无法读到 E3。查询不会消费待处理投递、另发投递或启动 Run。A 可在 S 写、查、读 Note，无法将这些操作扩大为插件安装。 |
| 同一插件包启用两个实例。给 A 的两个实例分别填入不同值，再给 B 的同一实例填入第三个值 | 在相应 Agent 下实际调用每个实例，处理函数从 `ctx.agent_config` 读到各自通过 schema 校验的值，实例 Settings 保留原值。对目标实例提供不合 schema 的值，创建报错，查不到半成品 Agent。 |
| 让获授权的创造者在当前 Session 查到 CI 日志的 Note，编写只读错误码提取工具，安装并在测试范围启用、绑定，然后调用它 | 创造者能从实际生效的目录发现新工具，用原 Note 引用提取正文中的 `E421`。ToolCall 可查到实际执行的插件实例、版本和结果，CI 仍只执行一次。停用后，下一轮目录撤下该入口，旧绑定再次派发的执行次数为零，原 ToolCall 仍可查。 |
| 让普通 Agent 请求安装插件，让缺少目标授权的 `creator` 尝试修改其他 Agent 的绑定或越范围启用插件 | 宿主拒绝操作，目标的生效修订、绑定和启用状态均可查证保持原值。选用模板或自行编写插件产生的额外管理授权为零。 |

## 开放能力

- Rust 宿主通过 `PluginProvider` 提供插件契约，本期使用 `LuaPluginProvider`。内置默认实现可运行，第三方 Lua 插件可按同一机制订阅事件或参与扩展点。推理触发与输入构建可独立替换。
- 内置工具、Lua 工具和通过 Lua 接入的 MCP 工具默认经 Code Mode 调用。显式声明直接调用的工具只走模型原生入口。同一轮可以核实两种入口分别允许调用哪些工具。
- 插件可注册 REST 服务、settings 和 prompt section。插件设置通过 `/api/settings/{plugin}` 配置，插件调用上下文取得实际生效的值。
- 本期支持普通 Agent 自查与事件回看，以及获授权的创造者查阅版本化指南、开发和启停插件、用真实工具调用验证效果。Run 内按需开启工具集仍为候选，示例管理工具名和具体分包可在实现时细化。

## 首版边界

首版 Goal 服务于一次 Run 内的交办。跨多个 Run 管理独立目标留待后续评估。本期暂缓专门的子 Agent 委派与父子 Run 调度、工作环境和文件检查点恢复、跨 Session 记忆、独立 outcome 验收插件及官方 `read_skill`。工作区指令文件的发现由接入方负责。事件总线默认使用 SQLite 本地分发，部署方也可选择 Redis Streams，插件沿用同一订阅接口。持久化后端、对外托管通用订阅、具体的 REST 和事件名称、官方插件分包及示例工具清单仍可在实现设计中细化。
