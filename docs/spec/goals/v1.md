# 首版目标与验收

loom-harness 为云端 Agent 提供上下文和运行管理。调用方可以定义 Agent，将交办或材料投给它，在并行调用和长时间等待后取得约定的结果。官方及第三方插件可以扩展模型、工具、上下文和投递行为。

首版范围已经确定。以下场景用于检验后续实现；当前仓库记录的是设计，运行代码与验收结果尚待交付。

## 单次交办能持续到履约

| 场景 | 可观察的结果 |
| --- | --- |
| 普通交办要求根据已提供的报告回答问题 | 模型正常返回最终答复，本轮没有工具请求，交付所需的材料和结果都已齐备。宿主按原交付约定返回答复并结束 Run。 |
| 在一个 Session 中要求 Agent 查两份报告并综合结论 | 同一 Run 可以多次调用模型和工具。先返回的子调用交回实际调用者，另一项仍可继续。最终结论包含两项结果或各自明确的失败原因。 |
| 普通交办要求交付最终报告，工具先返回作业号，期间 worker 重启 | 原 Run 登记等待并释放 worker，稍后按调用与作业标识接回报告。这条路径无需启用 Goal。重复回执只能推进同一次等待一次。对外部动作结果未知时，可以查到其未决状态。 |
| 原交办约定“仅在失败时通知” | 检查成功并记录结果后即可完成。需要通知时，系统保存答复和目标，按约定的交付条件结束。发送重试沿用原答复。 |
| 用户给已有交办补充要求或请求取消 | 外部通过事件向所属 Session 投递并关联原 Run。已受理的补充可参与后续判断；接受取消后停止新派发，迟到回执仍可追溯到原调用。 |

## 显式启用 Goal 的交办

| 场景 | 可观察的结果 |
| --- | --- |
| 交办时启用官方 Goal 插件，要求“迁完 20 个模块，并跑通全量测试”。模型在迁完 14 个后给出阶段总结，此时没有在途工具 | 首轮总结记入原 Run 的进度。插件请求在原 Run 中继续推理，无需用户再发消息。模型核对 20 个模块的迁移结果和全量测试通过的报告后，显式标记 Goal 完成。宿主按原约定对外交付最终答复。 |
| 追查迁完第 14 个模块后如何续跑 | 原 Run 中可查到持久保存的推理请求，原因是 Goal 续跑。重放同一次续跑决定时仍可查到同一个请求。此次续跑没有新增 EventDelivery 或 Inbox 收件，聊天界面也没有新增用户发言。 |
| 使用已压缩的历史构建这次续跑输入，再重试同一请求 | 实际发给模型的 message list 仍包含当前迁移目标和“20 个模块全部迁完、全量测试通过”的完成条件。所选历史之后有一条内部续跑说明，角色为 `user`，来源标为 `goal`。重试后这条说明仍只出现一次。后续调用按各自的推理原因组装输入，旧说明不会随历史或摘要累积。 |
| Goal 运行期间，下一步需要等测试作业返回 | 沿用 Run 的等待记录。期间不因 Goal 仍在进行而反复调用模型。若接受取消或耗尽约定预算，停止自动推进，保留实际停止原因。 |
| 同一迁移交办已提交全量测试 T42。等待期间历史被压缩，随后同一份失败回执到达两次 | 回执归入 T42。原 Run 只登记一次分析失败的主推理，触发原因为工具回执满足等待。实际发给模型的输入包含当前迁移目标、完成条件和失败报告或可回读的引用。该轮的 Goal 主动续跑说明为 0 条，T42 只提交过一次。 |
| 为分析 T42 的失败报告而压缩历史时，用户收紧要求为“只分析，别重跑”或取消交办，随后旧摘要就绪 | 收紧要求生效后，新一轮实际输入包含该限制，旧的重跑建议不会被派发。若取消已生效，失败回执仍可查，迟到或重复的摘要不会重新启动原 Run。 |
| 组装 Goal 所需输入时发生不可恢复的压缩错误 | 原 Run 记录可查询的失败原因，停止针对同一错误的主动重试。 |

## 用户可指定模型、图片输入和最终结果

| 目标 | 验收时检查什么 |
| --- | --- |
| 模型选择 | 给 Agent 配置可用模型，发起一次交办。从该轮调用记录能核实实际使用的模型。 |
| 故障切换 | 配置兼容的备选并让首选模型临时不可用。原 Run 按配置继续，主备尝试可区分；已经派发的工具仍按原调用处理。没有满足本轮能力要求的备选时，调用方能取得失败原因。 |
| 用户图片输入 | 用户提交文字和图片。检查提供方收到的实际请求中包含可解析的图像内容；图片引用不可读时可查到失败原因。 |
| 结构化结果交付 | 调用方随交办约定最终结果的结构。宿主校验准备交付的最终值，调用方取得满足约束的结果或明确的校验失败。中间工具的返回格式按该工具自己的契约处理。 |

联动验收可使用一张带已知用例名和错误码的失败截图，要求输出两个指定字段。首选模型临时不可用后，支持图片的备选应读到原图，交付值通过约定结构校验，并能追溯同一 Run 的两次尝试。模型选择的配置字段、允许切换的错误分类与具体重试次数仍待接口评审。

## 上下文与事件投递

| 场景 | 可观察的结果 |
| --- | --- |
| 同一条构建报告既要给归档 Session 留档，又要请值班 Agent 排查 | 两次投递可独立查询并引用同一 Event。留档只增加材料；交办才建立 Run。即时、定时和条件投递可通过同一安排机制配置。用户经 REST、获授权的 Agent 经工具管理同一份安排；Lua 规则可以决定是否发送、内容和目标。 |
| 历史逐步超出模型输入预算 | 官方压缩能力使所选历史可以压缩后参与模型调用。可以检查压缩覆盖的历史和本次实际采用的内容。当前交办、未决工具状态以及原事件仍可追溯。 |
| 从已有会话某个历史位置创建分支 | 官方 branch 插件创建可独立继续的子 Session。能核对来源和切点，从子会话继续交办。原会话的活动 Run、待完成工具调用以及结果仍由原所有者接回。 |
| 工具集注册了一段说明，后续刷新或撤出 | Session 启动时按适用范围组装 section，后续模型调用看到最新有效内容。每轮 message list 可按扩展策略选择、排序、编辑材料。 |

## 开放能力

- Rust 宿主通过 `PluginProvider` 提供插件契约，本期使用 `LuaPluginProvider`。内置默认实现可运行，第三方 Lua 插件可按同一机制订阅事件或参与扩展点。推理触发与输入构建可独立替换。
- 内置工具、Lua 工具和通过 Lua 接入的 MCP 工具默认经 Code Mode 调用。显式声明直接调用的工具只走模型原生入口。同一轮可以核实两种入口分别允许调用哪些工具。
- 插件可注册 REST 服务、settings 和 prompt section。插件设置通过 `/api/settings/{plugin}` 配置，插件调用上下文取得实际生效的值。Skill 简介和正文按需披露，可由其接入工具提供。
- Agent 自查、版本化文档、编写和动态启用插件、Run 内按需开启工具集均保留为候选设计。可用“读当前版本、提交修改、观察实际效果、修订或停用”来评审其闭环；具体操作、命名和默认开启范围待定。

## 首版边界

首版 Goal 服务于一次 Run 内的交办。跨多个 Run 管理独立目标留待后续评估。本期暂缓专门的子 Agent 委派与父子 Run 调度、工作环境和文件检查点恢复、跨 Session 记忆、独立 outcome 验收插件及官方 `read_skill`。工作区指令文件的发现由接入方负责。存储与总线选型、对外托管通用订阅、具体的 REST 和事件名称、官方插件分包及示例工具清单仍可在实现设计中细化。
